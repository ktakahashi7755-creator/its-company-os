# AI受託事業スキル

第2の柱。**SESで信頼を得た顧客に、現実的な価格でAIによる業務改善を提供する「実装できる相談相手」**になる。粗利率40〜60%。2027年から本格化（2026は種まきのみ）。

> 経営原則は `../../CLAUDE.md`。2026年のうちはSESを圧迫しない範囲で「ヒアリングと小さなPoC」までに留める。

## ワークフロー（リード → 納品）

1. ヒアリング → 2. 課題の構造化 → 3. スコープ/提案 → 4. 見積 → 5. 要件定義 → 6. 開発 → 7. 納品 → 8. 保守/横展開

---

## 1. ヒアリング

「AIで何かしたい」は要件ではない。**業務のどこに時間とお金が消えているか**を引き出す。
```
現状の業務フロー：
時間/コストがかかっている工程：
理想の状態：
既存システム/データの状況：
体制・予算感・期限：
社内の意思決定者：
```

## 2. 課題の構造化と打ち手の型

| 顧客の悩み | 典型的な打ち手 |
|---|---|
| 問い合わせ対応が重い | AIチャットボット（FAQ＋有人エスカレーション） |
| 社内の情報が散在 | 社内ナレッジAI（RAG：社内文書検索＋要約） |
| 定型作業が多い | 生成AIで下書き自動化・分類・要約 |
| 紙/手入力が多い | OCR＋構造化（Familinkの知見が活きる） |
| ツールがない | 小規模システム/アプリ開発 |

**重要：AIが手段として最適か常に問う。** ルールベースや既存SaaSで足りるなら、それを正直に勧める（信頼が次の案件を生む）。

## 3. スコープ設計

- **PoC（小さく始める）→ 本開発 → 保守** の3段で提案すると意思決定が進みやすい。
- スコープは「やること/やらないこと」を明記。スコープクリープ（際限ない追加）を防ぐ。

## 4. 見積

`../../templates/estimate-jutaku.md` を使う。考え方：
- 工数（人日）× 単価 ＋ ツール/API費 ＋ バッファ（リスク分15〜20%）。
- 生成AIのAPI従量課金は顧客負担 or 見積に明記。
- 粗利率40〜60%を確保（SESより高い＝バリュエーションに効く）。
- 保守/運用は月額（ストック収益）で提案。

## 5. 要件定義 → 開発 → 納品

- 要件定義書で「入力/出力/成功基準/対象外」を合意してから着手。
- 開発はFamilinkの技術資産（React/TS/Supabase/AIアシスタント設計）を再利用してコスト圧縮。
- 納品時：動作確認・引き継ぎ資料・保守提案をセットで。

## 6. 横展開

- 1社の成功事例を匿名化して他のSES顧客へ展開（CACを最小化）。
- 実績は会社の信用資産。事例として（顧客許諾の範囲で）蓄積する。

詳細な提案書の構成・PoCの進め方は `references/delivery.md` を参照。

## ガードレール
- 顧客が入力すべき認証情報を会社側が代行入力しない（全業務共通）。
- 過剰な期待を煽らない。できること/できないことを正直に。
- 個人情報・機密データの扱いは契約で明確化（取扱範囲・保管・削除）。
