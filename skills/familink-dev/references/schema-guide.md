# Familink スキーマ設計ガイド（reference）

DBスキーマ先行の原則を実務に落とすための規約。実装はFamilinkリポジトリ側で行うが、設計判断の基準をここに固定する。

## 設計の順序
1. ドメインのエンティティを洗い出す（family, member, event, task, expense, health_record, photo など）
2. リレーションを決める（family が中心。多くのテーブルが family_id を持つ）
3. RLS（Row Level Security）を必ず設計：**家族メンバーは自分の家族のデータのみ参照/編集可**
4. カラムの型・NULL可否・デフォルト・インデックスを決める
5. マイグレーションとして管理（履歴を残す）

## 共通方針
- すべての主要テーブルに `id`(uuid) / `created_at` / `updated_at`。
- 家族スコープのテーブルは `family_id` を必須にし、RLSで縛る。
- 個人に紐づくものは `member_id` を持つ。
- 物理削除より論理削除（`deleted_at`）を検討（家族の記録は消えると困る）。
- 認証は Supabase Auth。**パスワード・認証コードは本人入力。運用側で代行しない。**

## ドメイン別の留意点
- カレンダー（event）：繰り返し予定（recurrence）の設計を最初に決める。後付けは高コスト。
- 家計（expense）：金額は整数（最小通貨単位）で保持。カテゴリは正規化。
- 体調（health_record）：センシティブ情報。RLSと共有範囲を特に厳格に。
- 写真（photo）：Supabase Storage。メタデータはDB、実体はStorage。
- OCR予定読み取り：抽出結果は「下書き」として保存し、ユーザー確認後に正式なeventに昇格。

## やらないこと
- スキーマを決めずにUIから作り始める。
- RLSを後回しにする（セキュリティは最初から）。
- センシティブ情報の共有範囲を曖昧にする。
