# Familink開発スキル

家族向けスーパーアプリ。**短期売上ではなく、企業価値（将来のSaaS ARR）を作る資産。** 急がず、設計を崩さず、着実に積む。SES業務を圧迫しない最小工数で進める（夜・週末枠）。

> **GitHub上のFamilink開発リポジトリと紐付け済み。** 経営OS（CPO_Product_AI/CTO_Technology/取締役会）が優先順位を決め、それをFamilinkリポジトリの `docs/product-roadmap.md` に書く＝両チームの正本。実装はFamilinkリポジトリのClaude Code（既存CLAUDE.md＋skills）が、その roadmap と `docs/design-principles.md` を読んで行う。配線の実体と導入手順は `../../bridge/familink/`。経営OS側の優先順位の出所は `../../docs/roadmap.md`（Phase 2でFamilink公開）。

## 絶対原則

1. **DBスキーマ先行。** 機能を作る前に必ずデータモデル（テーブル・カラム・リレーション・RLS）を設計する。UIはスキーマに従う。
2. **顧客（ユーザー）が入力すべき認証情報を、アプリ/運用側が代行しない。** パスワード・認証コードは本人入力（全業務共通の絶対ルール）。
3. **デザイン原則を崩さない**（下記）。

## デザイン原則（一貫して守る）
- 装飾的な絵文字は使わない
- アイコンはライン系（line-art）
- 落ち着いた配色（calm palette）
- 余白を活かす（whitespace）
- コピーは簡潔な日本語
- ライトモードでも崩れない（共有時の表示安定）

## 技術スタック
- フロント：React + TypeScript + Vite + Tailwind CSS
- バックエンド：Supabase（DB・認証・ストレージ・RLS）
- AIアシスタント：Hoku

## 機能ドメイン
家族カレンダー / タスク管理 / 家計管理 / 体調管理 / 写真管理 / OCR予定読み取り / 家族共有

## 実装ワークフロー（機能追加時）
1. **スキーマ設計**：必要なテーブル/カラム/リレーション/RLSポリシーを定義（`references/schema-guide.md`）
2. **型定義**：Supabaseスキーマから TypeScript 型を生成・整合
3. **API/データ層**：取得・更新の関数を先に固める
4. **UI**：デザイン原則に沿って実装。コンポーネントは再利用前提
5. **Hoku連携**：その機能でHokuが助けられること（例：予定の要約・リマインド）を検討
6. **権限/共有**：家族メンバー間の共有範囲とRLSを必ず確認

## Hoku（AIアシスタント）の設計方針
- 役割：家族をそっと手伝う案内役。出しゃばらない。
- トーン：やさしく簡潔な日本語。装飾過多にしない。
- できること例：次の予定の案内、予定の自動読み取り（OCR）、タスク/買い物の整理。
- 安全：個人・家族の情報を扱う前提で、データの取扱範囲を明確に。認証情報は代行しない。

## マネタイズ（急がない）
- フリーミアム → 家族プラン月額（サブスク）。
- 2028にARR種、2029にARR ¥3,000〜5,000万を目標（`../../docs/financial-model.md`）。
- ARR・継続率（チャーン）がバリュエーションの核。機能より「使い続けられる体験」を優先。

スキーマ設計の詳細規約は `references/schema-guide.md` を参照。
